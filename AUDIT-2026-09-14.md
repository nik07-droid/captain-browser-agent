## Changes made

- Blank/new tabs can start navigation without waiting for an unavailable content script. Clarifications are handled in the extension worker, so a blank page can answer “Which website?”
- One Incognito target is retained between commands. An explicit “in a new tab” request creates a target in that same window; follow-up commands use its saved binding.
- Minimized or title-bar-sized windows are restored to a usable viewport for playback. Actions use the latest observed DOM references, not stale duplicate attributes.
- Playback confirmation requires a matching title, stable page/source identity, no detected ad and an advancing clock. Accepted play calls are not sufficient evidence. Paused requested media can be resumed at most twice while verifying.
- Cancel stops subsequent actions, including cancellation during debugger attachment. Already-sent actions cannot be undone.
- Wake phrase plus command can be one utterance. Missing details prompt a follow-up; typed and spoken answers share the same completion logic. Awake listening times out after 20 seconds. Completion returns to sleep.
- “Put on”, “listen to”, polite requests, pause and resume use the tested command path. Model-only completion is marked **Review required**, not independently verified success.
- Only the controller announces completion, preventing duplicate website-overlay announcements.
- Raw screenshot uploads remain disabled. The privacy boundary checks decoded strings rather than inventing email addresses from JSON newline escapes.

## How to try voice

1. Run `START-CAPTAIN.cmd` in the project, or `npm run demo` there.
2. Use the CAPTAIN controller tab in the dedicated Incognito window. Keep it open.
3. Click **Speak** and allow microphone access.
4. Say **“wake up captain”**, wait for the prompt, then **“open YouTube”**. Alternatively say **“Captain, open YouTube”** in one utterance.
5. After completion, wake it again and say **“play Arijit Singh songs”**. Use **“pause”** for the next command.

The **You said** text shows the recognized command. If it differs from what you spoke, that is a speech-recognition problem, not evidence that the intended command reached the executor. Mic off disables wake listening. Reloading the extension requires enabling the microphone again.

## Important remaining work

- Real microphone, wake/noise, echo and audible-response testing with the user. Voice state-machine tests use simulated recognition events.
- Local wake-word/STT/TTS and a persistent companion/native-messaging service. Current Chrome speech recognition may send audio to its online service even while waiting for the wake phrase.
- Learned local visual perception, OCR/face detection and measured comprehensive redaction. Current DOM regex filtering can miss PII; Incognito is not a privacy guarantee.
- Reliable general task planning. Ollama is configured with `qwen2.5:0.5b`; the tested common commands do not depend on that small model. UI-TARS source is a reference, not an integrated runtime.
- Twenty-run reliability gate, broader recovery/security review, resource measurements, SIH dataset evaluation, installer and validated Firefox/store packaging.

## Design basis

CAPTAIN borrows the intent/detail/clarification/session pattern documented in [Alexa's interaction model](https://developer.amazon.com/en-US/docs/alexa/custom-skills/create-the-interaction-model-for-your-skill.html) and [request/response sessions](https://developer.amazon.com/en-US/docs/alexa/custom-skills/request-and-response-json-reference.html). This is not Amazon's implementation. [Chrome's play-promise documentation](https://developer.chrome.com/blog/play-returns-promise) explains why accepted playback can be deferred in a hidden tab; the extension now checks observable playback instead.
